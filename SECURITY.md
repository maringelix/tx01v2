# Security policy

## Reporting a vulnerability

Report privately through GitHub: **Security > Report a vulnerability** on this repository (private
vulnerability reporting is enabled when the repository is public, see `docs/PUBLISHING.md`). Do not
open a public issue. Never include credentials, AWS account IDs or IP addresses; use placeholders.

This is a personal educational project: reports are handled on a best-effort basis, with no response
time guarantee and no bug bounty.

## Supported versions

Only the latest commit on `main`. There are no releases yet.

## What this repository does to stay safe

The rules, where each one is enforced and the known limits are in
[docs/GUARDRAILS.md](docs/GUARDRAILS.md). In short:

- The harness (`make verify`, also the CI) runs gitleaks, trivy (HIGH/CRITICAL), tflint, actionlint,
  shellcheck, kubeconform and policy checks that block real identifiers, unpinned actions and the
  regressions found in v1.
- GitHub Actions reach AWS only through OIDC roles with exact `sub` claims; there are no static keys.
- Database password and admin token are generated by ephemeral resources and written with write-only
  arguments: they are never stored in the Terraform plan or state.
- Every harness tool is pinned by version and SHA256; actions by commit SHA; images by digest.

## Known limits

v2 has never been applied to AWS (`not run in the cloud (v2)`): the Terraform tests use a mocked AWS
provider. The apply role has high privileges within the AWS service families the lab uses. Service
creation APIs do not always support resource-level restrictions. IAM, the state and Velero buckets,
and optional Route53 records have narrower scopes. Workload roles created by apply have a boundary
that limits S3 to the Velero bucket and Route53 to the configured zone. Use a **dedicated AWS account** and keep the `lab`
environment protected.
The lab account ID appears in public workflow logs. See the "Limites" section of docs/GUARDRAILS.md.
